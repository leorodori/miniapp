## 2. このアイデアはどこから生まれたか

### 2-1. きっかけとなった体験・感情
- **いつ・どんな状況で**: 
  本（紙媒体）、Web記事、映画、音楽、そしてお笑いのネタやバラエティ番組での発言など、日常のあらゆる場面で「心に刺さる言葉（感動やクスッと笑えるフレーズ）」に出会ったとき。
- **どんな気持ちになったか**: 
  あとからその言葉を見返そうとしても、媒体ごとに記録が散乱していたり未記録だったりして、探す場所が見つからない。「あの言葉、どこにあったっけ…？」といちいち探す時間や手間が非常におっくうで、イライラやモヤモヤを感じていた。

### 2-2. なぜそれが「気になった」のか
- **自分の価値観・経験**: 
  良い言葉との出会いを単なる一瞬の感情で終わらせず、「自分を勇気づける糧」や「生き方の指針」、あるいは「ちょっと気分を上げるユーモア」として大切にしたいという価値観を持っているから。だからこそ、せっかく出会った言葉が散逸してしまう状況に対して強い違和感・もったいなさを感じた。

## 3. 課題の整理

### 3-1. 表に見えている困りごと
- 出典（本、ネット、映画、歌、TV番組など）がバラバラで、心に残った言葉を1箇所に集めるまとめ先がない。
- 頭の中だけで記憶しようとしても時間が経つと忘れてしまい、スマホのスクショやXのブックマークなどは他の情報に埋もれてしまう。
- 探すために不要な時間と手間が奪われ、最終的に「探すこと自体を諦めてしまう」。

### 3-2. 本当に解決したい課題は何か
- **なぜ探すのが面倒だと困る？**
  → 言葉が必要になった「その瞬間」を逃してしまい、そもそも探すのを諦めてしまうから。
- **なぜ忘れてしまう・探すのに時間がかかると嫌？**
  → 時間が奪われるだけでなく、言葉に出会ったときの感動や「頑張ろう」「笑いたい」という熱量が冷めてしまうから。
- **なぜ言葉を活用できない状態が良くない？**
  → **本来、その言葉があれば頑張れたり、壁を乗り越えられたり、諦めずに済んだはずの場面で、自分を支える力を失ってしまうから。**

> **👉 本当に解決したい課題：**  
> 「出会った言葉をすぐに引き出せないせいで、困難に直面したときやモチベーションが必要な瞬間に、自分を支えてくれるはずの思考・感情の糧（言葉）を活用しきれていないこと。」

## 4. 想定ユーザーについて

### 4-1. 想定しているユーザー
- **ターゲット像**: 20代後半〜30代前半、新しいスキルの習得や仕事の成果に向けて日々挑戦・奮闘している社会人
- **生活・状況設定**: 仕事で壁にぶつかった夜や、一人で悩みを抱えがちな時間帯。
- **環境設定**: 本、Web記事、映画、SNS、テレビ・動画・ラジオなど音声/映像メディア（お笑い等）も含めて日常的にインプットを行っている環境。

### 4-2. 自分とユーザーの距離
- **距離感**: **自分自身**
- **理由**: 自分自身が日々仕事や学習の中で壁に直面し、「あの時感銘を受けた言葉」に助けられた経験がある一方で、情報が散乱して探せないストレスを直接体感しているから。

### 4-3. 実際に使われる可能性について（需要・存在確認）
- **代わりに使っているものと乗り換える理由**:
  1. **スマホの標準メモ**: ただの文字の羅列になり、「言葉」「出典」「どんな場面・文脈での発言か」を分ける専用の枠（構造）がないため、背景が残らず、記録自体が面倒になる。
  2. **Xのブクマ・スマホのスクショ**: 他の情報に埋もれて参照できず、紙の小説などはそもそもスクショが撮れない。
  3. **頭の中の記憶**: バラエティ等の発言は頭に留めるしかないが、クスッと笑いたい時に思い出せない。

### 4-4. ユーザーがサービスを導入して利用するまでのイメージ
- **最初の一歩（導入）**: 気になった言葉を1つ登録し、その言葉に出会った出典や「なぜ響いたか」のノートを一言添えて保存する。
- **継続利用の理由（習慣・価値）**: 
  1. 蓄積された言葉が「自分だけの思考・感情のライブラリ」になる。
  2. 壁にぶつかった時に自分の文脈付きで言葉をすぐに引き出せるため、「自分を支えてくれる体験」を実感し、使い続けたくなる。

## 5. 既存サービス・競合調査

### 5-1. 既存サービスの不満・ズレ
1. **汎用メモツールの違和感（Notion, Evernote等）**:
   - 自由度が高すぎるゆえに、「言葉」「出典」「文脈」を管理するためのフォーマットを自前で設計・構築するのが非常に面倒。スマホ標準メモでは文字の羅列になり見返すモチベーションが湧かない。
2. **名言集アプリの違和感**:
   - 並んでいるのは「他人が選んだ一般的な名言」ばかりで、自分自身の体験やその時の感情（自分が直接食らった時の文脈）と結びついていないため心に深く届かない。

### 5-2. 差別化を「体験価値」で表現する
> **「入力の手間なく、自分だけにしか理解できないが自分には確実に刺さる『感動』や『笑い』の言葉と、その時のエピソードを即座に取り出せる体験」**

- **体験の差分**:
  - フォーマット作成の手間ゼロで、「言葉」「出典」「場面/エピソード」を構造化して残せる。
  - 「自分の文脈（エピソード）」が紐づいた言葉だからこそ、見返した瞬間に確実に自分の力や笑顔に変えられる。

## 6. このサービスで提供したい価値

### 6-1. ユーザーの変化
* **行動の変化**:
  * 心に残る言葉に出会った際、迷わずこのアプリに記録するようになる。
  * 壁にぶつかった時や落ち込んだ時、まずこのアプリを開いて自分に必要な言葉を探すようになる。
* **気持ちの変化**:
  * 「あの言葉どこにあったっけ…」というイライラが解消される。
  * 「自分には自分を支えてくれる言葉のライブラリがある」という強い安心感が生まれる。
  * ノートを日記代わりに使うことで、その時の自分の感情や思考をそのまま吐き出せる場所ができる。
* **考え方の変化**:
  * 日常のインプットを「ただの消費」で終わらせず、「自分を形成する大切な糧」として前向きに捉えられるようになる。

### 6-2. 価値を一文で表す
> **「このサービスは、日常の中で心に響いた感動や笑いの言葉を大切にしたい人が、自分だけの文脈（エピソード）とともに言葉を蓄積し、壁にぶつかった時にいつでも自分を励まして乗り越えられるようになるサービス」**

## 7. このアプリで実現すること

### 7-1. MVP（初期リリース・現在実装済み）で作る機能
* **言葉管理機能（CRUD）**: 言葉の登録・一覧表示・詳細閲覧・編集・削除
* **ノート管理機能（CRUD）**: 言葉に紐づく背景・文脈・日記代わりの感情を記録するノートの作成・編集・削除
* **フォルダ管理機能（CRUD）**: 出典やテーマごとに整理・分類するためのフォルダ作成・分類・編集・削除
* **言葉のピン留め機能**: 特に大切にしたい言葉や、今すぐ見返したい言葉を固定表示する機能
* **言葉の検索機能**: 蓄積された言葉から、必要な言葉をキーワードで即座に引き出せる検索機能
* **サンプル閲覧モード（デモプレイ機能）**: 会員登録前でもアプリの使い勝手を体感できるお試し利用機能
* **ユーザー認証機能**: 個人の大切な言葉・文脈データを安全に保持・管理する機能
* **i18n対応（日本語化）**: エラーメッセージやUI表示を自然な日本語に完全対応
* **共通UIデザイン**: 統一感があり、入力や閲覧のストレスを減らすデザイン基盤

### 7-2. 本リリース（今後追加したい機能）
* **タグ付け機能**: フォルダによる階層整理に加え、複数の切り口（感情・属性）で言葉を横断検索できるようにする機能
* **ランダム表示 / 今日の言葉機能**: アプリを開いた際などに、過去の言葉をランダムに再提案し、大切な言葉との偶然の再会を演出する機能

## 8. このアプリの懸念点とその対策

### 懸念点①：インプット（登録）の習慣化のハードル
- **懸念**: 「言葉を残すのが面倒」になって登録をやめてしまう可能性がある。
- **対策**: 入力項目の構造化により手軽に入力できるようにする / 検索やピン留めなど「残した後の恩恵」を最大化する / サンプル閲覧で完了形のイメージを伝える。

### 懸念点②：著作権・引用に関する懸念
- **懸念**: 書籍やテレビ発言などの引用における著作権上の問題。
- **対策**: 完全プライベート（非公開メモ）を前提としたデータ設計にし、個人の私的利用の範囲内で安心してデータを蓄積できるようにする。

### 懸念点③：データ蓄積前の初期ユーザーの離脱
- **懸念**: 登録数が少ない初期状態では価値を感じにくい。
- **対策**: デモプレイ（サンプル閲覧機能）を標準実装し、使い込んだ状態の体験イメージを最初に提示する。

### 10-2. 技術選定の理由・比較検討
1. **なぜバックエンドに Ruby on Rails を選んだのか？**
   - CRUDを中心としたデータ構造と、認証・i18nなどの標準機能を短期間でセキュアに構築できる「CoW（設定より規約）」の思想を最優先しました。
2. **フロントエンド・CSS設計の工夫（共通化とコンポーネント指向）**
   - Sprocketsアセットパイプラインを活用し、`components/` 配下にスタイルを分割。リンク（`.link-action`）やエラー表示（`.error-messages`）を共通化し、`Noto Serif JP`（明朝体）を基調とすることで、言葉とじっくり向き合える静かで美しいUI体験を実現しました。
3. **ビルドフリーなJS構成（Importmaps + Hotwire）**
   - MVPでの迅速な価値検証を最優先し、Node.js依存の複雑なビルドツールを排除できる構成を選択しました。
4. **コンテナ化（Docker）の採用**
   - インフラ構成をコード化（IaC）し、環境依存のないスムーズな開発・デプロイ環境を実現しました。

### 10-3. 今後の技術的展望・キャッチアップ計画
* **フロントエンドのモダン化（React / Next.js 移行の検討）**:
  - UIのさらなるリッチ化・インタラクティブ化に向け、React（または Next.js）を導入し、RailsをAPIモードとして切り離すSPA化のキャッチアップを検討。
* **非同期処理・通知機能の拡張**:
  - リマインド通知機能や傾向分析を見据え、RedisやSidekiqなどのバックグラウンドジョブ基盤の導入を視野に入れています。
